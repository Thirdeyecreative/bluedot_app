## 1. Executive Summary & Legal Mandate

Under the amended provisions of the **Finance Act** and **Rule 18AB of the Income-tax Rules, 1962**, a physical or PDF receipt issued by an NGO is **no longer legally sufficient on its own** for a donor to claim a tax deduction under Section 80G.

To ensure 100% legal compliance, zero tax rejection for donors, and complete immunity from administrative penalties:
1. **Donor Identification (PAN/Aadhaar)** must be collected and validated prior to transaction settlement.
2. **Form 10BD (Statement of Donations)** must be filed electronically on the Income Tax e-Filing Portal on or before **May 31st** following the close of the financial year.
3. **Form 10BE (Certificate of Donation)** is generated by the Income Tax Department within 24 hours of Form 10BD submission, containing a unique **Acknowledgement Reference Number (ARN)** that pre-populates in the donor's **Annual Information Statement (AIS)** and **Form 26AS**.
4. BlueDot provides an immediate system-generated interim **Section 80G Statutory Receipt** with cryptographic verification hashes, URN details, and statutory Rule 18AB advisories.

## 4. ACID Compliance Verification in Financial Ledger

Financial transactions in BlueDot are engineered to satisfy **ACID** properties without compromise:

### 1. Atomicity (All or Nothing)
* **Problem Prevented:** Partial failure where money is captured, but user XP points fail, campaign raised total doesn't increase, or the 80G receipt record is lost.
* **Implementation:** All updates occur in a single database transaction in `_settle_donation_success`:
  ```python
  try:
      # Step 1: Lock AppUser row
      user = db.query(AppUser).filter(AppUser.id == donation.user_id).with_for_update().first()
      # Step 2: Mark Donation Completed
      donation.payment_status = "Completed"
      db.add(donation); db.flush()
      # Step 3: Credit XP & Total Donated
      user.total_donated += donation.amount
      user.total_impact_points += xp_awarded
      # Step 4: Recalculate Campaign Funds (commit=False)
      sync_campaign_raised_amount(db, donation.campaign_id, commit=False)
      # Step 5: Issue 80G Receipt
      receipt = Receipt80G(...)
      db.add(receipt)
      # Final Atomic Commit
      db.commit()
  except Exception as exc:
      db.rollback()  # 100% rolled back, zero orphaned state
      raise HTTPException(500, detail="Settlement aborted")
  ```

### 2. Consistency (State Invariants)
* **Problem Prevented:** Corrupted or divergent campaign totals.
* **Implementation:** 
  $$\text{Campaign.current\_amount\_raised} = \sum \text{Completed Donations} - \sum \text{Refunds}$$
  * A donation cannot generate multiple receipts (`unique=True` on `80g_receipts.donation_id`).
  * Non-negative bounds enforced on amounts (`ge=Decimal("10")`, `le=Decimal("500000")`).

### 3. Isolation (Pessimistic Row Locking)
* **Problem Prevented:** Concurrency race conditions if the mobile client verification call and Cashfree's asynchronous webhook strike the server within the same millisecond.
* **Implementation:** 
  ```python
  donation = db.query(Donation).filter(Donation.payment_gateway_ref == order_id).with_for_update().first()
  ```
  PostgreSQL locks the `donations` and `app_users` rows via `SELECT ... FOR UPDATE`. The first thread acquires the lock and transitions state to `Completed`. The second thread waits, acquires the lock, observes `payment_status == 'Completed'`, and safely exits without double-crediting.

### 4. Durability (Write-Ahead Log)
* **Problem Prevented:** Data loss if server power or process dies.
* **Implementation:** PostgreSQL WAL guarantees that once `db.commit()` returns, all mutations are durably written to persistent NVMe disk before the HTTP response or Redis cache invalidation occurs.

## 5. CAP Theorem: Prioritizing CP (Consistency & Partition Tolerance)

In distributed financial architectures comprising **Cashfree Payment Gateway**, **FastAPI Backend Servers**, and **Supabase PostgreSQL Clustered Storage**, the system is explicitly designed around **CP (Consistency + Partition Tolerance)**:

1. **Zero Optimistic/Speculative Credits**: If network communication with Cashfree drops or times out during checkout, the backend **refuses** to guess. The donation remains `Pending` / `Under Review`.
2. **Double Verification**: BlueDot never trusts the mobile client's claims. Even if the Flutter SDK reports success, our backend directly queries Cashfree's bank settlement API (`GET /pg/orders/{order_id}`) to confirm `order_status == "PAID"` and amount exactness.
3. **Idempotent Webhooks with Clock Drift Protection**: Webhook payloads are verified using Cashfree's HMAC-SHA256 signature and rejected if timestamps drift by more than 300 seconds, preventing replay attacks across network partitions.
4. **Automated Reconciliation**: If a partition occurs, our reconciliation worker (`reconciliation_service.py`) periodically synchronizes pending orders directly with Cashfree's ledger, restoring system consistency automatically when connectivity resumes.

## 6. Official Form 10BD CBDT Export Format

The export endpoint (`GET /api/v1/admin/finance/export/form-10bd`) generates a CSV file with the 12 mandatory columns specified by the Directorate of Income Tax (Systems):

1. **Sl. No.**: Sequential integer index.
2. **Internal Receipt / Pre-acknowledgement No.**: BlueDot 80G receipt number (`BD/80G/2026-27/...`).
3. **ID Code**: `1` for PAN, `2` for Aadhaar.
4. **Unique Identification Number of the Donor**: 10-character alphanumeric PAN.
5. **Section Code**: `Section 80G`.
6. **Unique Registration Number (URN) of NGO**: `AAATB1234C/80G/2023-24`.
7. **Date of Issuance of URN**: `24-05-2023`.
8. **Name of Donor**: Donor's legal name matching IT records.
9. **Address of Donor**: Country / jurisdiction.
10. **Donation Type**: `Specific Grant (Restoration)` or `Corpus`.
11. **Mode of Receipt**: `Electronic (UPI/Gateway)`.
12. **Amount of Donation (INR)**: Numerical integer donation amount.
